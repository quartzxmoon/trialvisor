# Tests

## Test 1 - Public trust surfaces and first-time onboarding [sanity]
Viewport: desktop (1280x800)
Covers: public landing, How It Works, Security, Provider Support, Subprocessors, authentication, account initialization, resumable onboarding
Description: Verifies that public education and trust pages are reachable without authentication, make the authorization boundaries explicit, and preserve first-run account setup.

Steps:
1. Open the landing page and visit How It Works, Security, Provider Support, and Subprocessors from public navigation
2. Confirm the lifecycle reads Connect, Discover, Review, Protect, Monitor, Decide, Cancel, Verify
3. Sign in with a first-time Trialvisor identity, refresh during onboarding, then continue without connecting an inbox

Expected: Public pages render without a session; they state that inbox connection and detection do not authorize cancellation, do not advertise any provider as Autopilot, list only confirmed production dependencies, and expose a security-reporting route. The new user resumes onboarding after refresh and reaches the protection center only after completing setup.

## Test 2 - Review, Protect, notifications, and customer activity are durable
Viewport: desktop (1280x800)
Covers: manual finding, REVIEW_REQUIRED, explicit Protect, Safe Cancel Deadline, persistent notifications, per-trial audit timeline
Description: Verifies that detection remains separate from authorization and meaningful events survive navigation and refresh.

Steps:
1. Add a manual Canva Pro trial at $14.99 per month with a future end date
2. Open its activity timeline and Notification Center
3. Open Protect, review the annualized cost and authorization language, and select Protect this trial
4. Refresh, mark a notification read, and refresh again

Expected: The finding begins in REVIEW_REQUIRED; its timeline distinguishes user action, Trialvisor action, and provider result. Protection activates only after explicit confirmation. Protection and notice read state persist after refresh, while critical entries remain available.

## Test 3 - Neutral decisions, Data Controls, and safe feedback
Viewport: desktop (1280x800)
Covers: KEEP path, durable scheduling revocation, data export, data-retention explanation, contextual feedback, guarded account deletion
Description: Verifies customer controls are understandable and cannot leak sensitive provider credentials.

Setup:
1. Add and protect a manual trial through the UI

Steps:
1. Select Keep service and refresh
2. Open Settings and review Accessed, Processed, Stored, and Retained explanations
3. Download the account export and submit an incorrect-date report
4. Open account deletion and cancel before final confirmation

Expected: Keep is durable and revokes scheduled cancellation. Export contains normalized account records but no OAuth tokens, secrets, or full email bodies. Feedback stores safe object context only. Account deletion requires an explicit second confirmation and is not performed when canceled.

## Test 4 - Connected Google account uses bounded, review-only discovery
Viewport: desktop (1280x800)
Covers: authenticated session restoration, Google connection state, Gmail sync, focused provider-side searches, HTML/plain-text parsing, versioned reprocessing, incremental history pagination and checkpoint fallback, confidence, deduplication, persistent sync status
Description: Verifies the dashboard and privacy-minimized Gmail processing recover a refreshable authenticated session without overstating real-mailbox validation.

Steps:
1. Connect Google through production OAuth, allow the access token to require refresh, and reload the application
2. Confirm the dashboard returns, then select Sync from Connected Accounts
3. Review the result, Notification Center, and any detected finding, then sync again after another session refresh

Expected: The refreshable AppDeploy session is restored before the dashboard or Sync request and a failed restoration shows explicit sign-in recovery instead of an endless loader. Account identity and last sync remain visible. Until the first real match, the bounded validation search can reprocess candidates handled by an older parser version; after validation, incremental history avoids unnecessary full searches and paginates within the cap. HTML-only and plain-text candidates can produce HIGH, MEDIUM, or LOW results. Processed messages store normalized signals and source references rather than full bodies, repeated sync does not duplicate findings, all findings remain REVIEW_REQUIRED, and no sync outcome grants cancellation authority. The result states its search mode, counts, confidence mix, and whether deduplication prevented a new item.

## Test 5 - Mobile failure safety and accessible navigation
Viewport: mobile (375x667)
Covers: primary navigation, Notification Center, Connected Accounts, persistent critical failure, keyboard/focus semantics, provider failure safety
Description: Verifies that core protection and recovery controls remain usable on a phone when Gmail is unavailable.

QA Faults:
```json
[
  {
    "method": "POST",
    "path": "/api/gmail/sync",
    "status": 503,
    "body_json": { "error": "gmail_temporarily_unavailable" }
  }
]
```

Steps:
1. Open mobile navigation, select Connected Accounts, and sync Google
2. Open Notifications and return to Protection
3. Traverse controls by keyboard and inspect focus, labels, and touch targets

Expected: The sync failure is persistently available with a contextual recovery action, failed discovery grants no authorization, navigation and dialogs fit at 375px, controls have visible focus and accessible names, status is not conveyed by color alone, and no cancellation is shown as verified without provider evidence.
